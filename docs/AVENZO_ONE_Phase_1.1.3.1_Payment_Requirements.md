# AVENZO ONE — Phase 1.1.3.1 Payment Requirements

อัปเดตล่าสุด: 8 สิงหาคม 2026

## เป้าหมาย

กำหนดความต้องการของระบบรับชำระเงินให้ชัดเจนก่อนเปรียบเทียบหรือสมัครผู้ให้บริการจริง เพื่อให้ AVENZO ONE เลือก Payment Provider จากช่องทางที่ลูกค้าต้องใช้ ความปลอดภัย การกระทบยอด และการดูแลหลังการขาย ไม่ใช่พิจารณาเฉพาะค่าธรรมเนียม

Phase นี้เป็นงานวิเคราะห์และเอกสารเท่านั้น ไม่มีการสมัครบริการ ไม่มีการเชื่อม API ไม่มีการเก็บ Secret Key และไม่มีการตัดเงินจริง

## ขอบเขตธุรกิจรุ่นแรก

- ตลาดเริ่มต้น: ประเทศไทย
- สกุลเงินหลัก: THB
- ผู้ชำระเงิน: Owner หรือผู้มีอำนาจชำระค่า Subscription ของ Organization
- รายการที่เรียกเก็บ: Plan และ Plan Version ที่ถูกบันทึกเป็น Invoice Snapshot แล้ว
- ระบบต้นทางของยอด: AVENZO ONE Billing เท่านั้น Provider ไม่มีสิทธิ์คำนวณราคา ส่วนลด หรือภาษีใหม่
- หน่วยอ้างอิงกลาง: Invoice ID, Invoice Number, Payment Attempt ID และ Provider Reference

## ช่องทางชำระเงินที่ต้องประเมิน

### ต้องมีสำหรับการเปิดใช้งานจริงรุ่นแรก

1. **PromptPay QR** — เหมาะกับลูกค้าไทยและการชำระ Invoice รายครั้ง
2. **บัตรเครดิต/เดบิต** — รองรับการชำระออนไลน์และเป็นฐานสำหรับ Auto-renew ในอนาคต
3. **โอนเงินผ่านธนาคารแบบตรวจสอบโดยเจ้าหน้าที่** — เป็นช่องทางสำรองเมื่อ Gateway ใช้งานไม่ได้หรือองค์กรต้องการโอนจากบัญชีบริษัท

### รองรับในสถาปัตยกรรม แต่ยังไม่บังคับเปิดรุ่นแรก

- บันทึกบัตรหรือ Token สำหรับ Auto-renew
- Recurring Payment และการต่ออายุอัตโนมัติ
- Mobile Banking Deep Link
- ช่องทาง e-Wallet
- Partial Payment, Installment และหลายสกุลเงิน

## ประสบการณ์ของลูกค้า

1. ลูกค้าเปิด Invoice ที่สถานะรอชำระ
2. ระบบแสดงยอดสุทธิ วันครบกำหนด ช่องทางที่ใช้ได้ และคำเตือนที่เข้าใจง่าย
3. ลูกค้าเลือกช่องทางและกดชำระ ระบบสร้าง Payment Attempt เพียงหนึ่งรายการต่อคำสั่ง
4. ลูกค้าถูกนำไป Checkout หรือได้รับ QR จาก Provider โดย AVENZO ONE ไม่รับข้อมูลบัตรเอง
5. หลังชำระ ระบบแสดงสถานะ `กำลังตรวจสอบ`, `ชำระสำเร็จ`, `ชำระไม่สำเร็จ` หรือ `หมดเวลา`
6. สถานะสำเร็จต้องมาจาก Webhook ที่ตรวจลายเซ็นแล้ว ไม่เชื่อผลจากหน้า Success ของ Browser เพียงอย่างเดียว
7. เมื่อตรวจสอบสำเร็จ ระบบอัปเดต Payment, Invoice และ Subscription อย่างสอดคล้อง พร้อม Audit Log
8. ลูกค้ากลับมาเปิด Invoice เดิมได้โดยไม่สร้างยอดเรียกเก็บซ้ำ

## การต่ออายุ Subscription

- รุ่นแรกใช้ **Manual Renewal**: ระบบแจ้งเตือนและให้ลูกค้ากดชำระแต่ละรอบ
- Auto-renew จะเปิดภายหลังเมื่อ Provider รองรับ Tokenization, Recurring Consent, Retry และการยกเลิกที่ตรวจสอบได้
- ห้ามเก็บเลขบัตรเต็ม, CVV หรือข้อมูลรับรองธนาคารใน AVENZO ONE
- การชำระสำเร็จต้องไม่ต่ออายุซ้ำเมื่อ Provider ส่ง Webhook เดิมหลายครั้ง

## Refund, Dispute และค่าธรรมเนียม

- รุ่นแรกต้องรองรับการบันทึก **คืนเงินเต็มจำนวน** และสถานะ `กำลังคืนเงิน`, `คืนเงินสำเร็จ`, `คืนเงินไม่สำเร็จ`
- Partial Refund และ Credit Balance เป็นระยะถัดไป แต่โครงสร้างข้อมูลต้องไม่ปิดกั้น
- ค่าธรรมเนียม Provider ต้องเก็บแยกจากยอดที่ลูกค้าชำระ เพื่อใช้กระทบยอดโดยไม่แก้ Invoice
- Dispute/Chargeback ต้องสร้างเหตุการณ์และแจ้ง Platform Admin ห้ามเปลี่ยน Subscription อัตโนมัติโดยไม่มีนโยบายที่อนุมัติ
- การคืนเงินจริงและนโยบายยกเลิกต้องผ่านการตรวจจากฝ่ายบัญชี/กฎหมายก่อนเปิด Production

## การกระทบยอด

Provider ที่เลือกต้องให้ข้อมูลอย่างน้อยดังนี้:

- Provider Payment ID และ Event ID ที่ไม่ซ้ำ
- ยอดเงิน สกุลเงิน สถานะ และเวลาที่ Provider บันทึก
- ค่าธรรมเนียม ภาษีค่าธรรมเนียม และยอดสุทธิที่รับจริง หาก Provider มีข้อมูล
- Settlement/Payout Reference และวันที่นำส่งเงิน
- รายงานหรือ API สำหรับตรวจรายการย้อนหลัง

ระบบต้องตรวจยอดและสกุลเงินตรงกับ Invoice Snapshot ก่อนรับเป็นชำระสำเร็จ และต้องแสดงรายการที่ยอดไม่ตรงหรือหา Invoice ไม่พบให้ Platform Admin ตรวจสอบ

## ข้อกำหนดด้านความปลอดภัย

- Secret Key และ Webhook Secret อยู่ฝั่ง Server และแยก Sandbox/Production
- Webhook ตรวจลายเซ็นจาก Raw Body ก่อน Parse หรือบันทึกผล
- ทุกคำสั่งมี Idempotency Key และทุก Event ป้องกันการประมวลผลซ้ำ
- Browser ไม่สามารถสั่งให้ Invoice หรือ Subscription เป็น Paid/Active โดยตรง
- Log ห้ามเก็บ Secret, ข้อมูลบัตร, Token เต็ม หรือข้อมูลส่วนบุคคลเกินจำเป็น
- การจัดการ Payment และ Refund ของ Platform Admin ต้องผ่าน MFA ระดับ AAL2, Permission และ Audit Log
- ต้องมี Rate Limit, Timeout และ Retry แบบควบคุมสำหรับ API ภายนอก

## ข้อกำหนดผู้ให้บริการสำหรับ Phase 1.1.3.2

ผู้ให้บริการที่จะผ่านเข้ารอบต้องมี:

- รองรับนิติบุคคลหรือธุรกิจในประเทศไทยและรับ THB
- มี PromptPay QR และบัตร หรือสามารถใช้ร่วมกับ Provider สำรองโดยไม่ทำให้ระบบผูกขาดกับรายเดียว
- มี Sandbox, API Documentation และ Webhook Signature ที่ชัดเจน
- มี Idempotency หรือวิธีป้องกันการสร้างรายการซ้ำ
- มี Dashboard, Transaction Search, Refund และ Settlement Report
- แจ้งค่าธรรมเนียม ระยะเวลารับเงิน เอกสาร KYC และข้อจำกัดธุรกิจอย่างโปร่งใส
- มีช่องทาง Support และสถานะระบบสำหรับเหตุขัดข้อง
- อนุญาตให้ AVENZO ONE ใช้ Checkout แบบ Hosted หรือ Tokenization โดยไม่เก็บข้อมูลบัตรเอง

## เกณฑ์ให้คะแนนผู้ให้บริการ

| หัวข้อ | น้ำหนักแนะนำ |
|---|---:|
| ช่องทางชำระและความเหมาะสมกับลูกค้าไทย | 25% |
| ความปลอดภัย, Webhook และ Idempotency | 20% |
| ค่าธรรมเนียมและระยะเวลา Settlement | 20% |
| Sandbox, API, Documentation และความง่ายในการเชื่อม | 15% |
| Refund, Reconciliation และรายงานบัญชี | 10% |
| KYC, Support, SLA และความน่าเชื่อถือ | 10% |

น้ำหนักนี้เป็นเกณฑ์คัดเลือกระยะแรก ยังไม่ใช่การตัดสินใจผูกสัญญาหรืออนุมัติค่าใช้จ่าย

## Acceptance Criteria

- มีรายการช่องทางที่ต้องมีและรายการที่เลื่อนไประยะถัดไปชัดเจน
- มีเส้นทางชำระสำเร็จ ไม่สำเร็จ หมดเวลา Webhook ซ้ำ และยอดไม่ตรง
- มีข้อกำหนด Refund, Fee, Settlement และ Reconciliation ขั้นต่ำ
- มีข้อห้ามด้านข้อมูลบัตร Secret และการเชื่อสถานะจาก Browser
- มีเกณฑ์เปรียบเทียบ Provider ที่ให้คะแนนได้
- ยังไม่มีการสมัคร Provider, ใช้ Secret, เรียก API หรือเรียกเก็บเงินจริง

## เรื่องที่ยังต้องตัดสินใจก่อน Production

- Provider หลักและ Provider สำรอง
- ผู้รับผิดชอบบัญชี Provider และผู้อนุมัติ Refund
- ค่าธรรมเนียม AVENZO ONE เป็นผู้รับภาระหรือส่งต่อให้ลูกค้า
- ระยะเวลาชำระ Invoice และนโยบายเมื่อเลยกำหนด
- นโยบาย Refund, Chargeback และการพัก Subscription
- เปิด Auto-renew เมื่อใด และข้อความ Consent ที่ฝ่ายกฎหมายอนุมัติ
- เอกสารภาษี/ใบเสร็จที่ต้องออกหลังชำระ
